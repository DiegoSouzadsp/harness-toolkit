# AD-146 — a linked worktree can read its own main checkout, and cd and git -C are locations, not writes

- **status**: active

## Decision

1. **`cd`/`pushd` denies outright when it lands inside the surface's own container, or when the segment's own
   text names the surface, even as the only segment in the command** (`landsInContainer`, `containerDirs`,
   and a restored `namesSurface` check in `checkCdSegment`). **A floor evaluation answers only from the one
   command string it was handed; it never reads the shell's own persisted cwd**, which is what actually
   carries between two separate Bash tool calls in the same session. `cd .tlc/harness` as one call, followed
   by `python3 -c "open('config.json','w')"` as a separate one, is two commands this gate sees in complete
   isolation from each other — the sticky `surfaceEntered` flag (below) only threads state *within* one
   command string, so it could not close this gap on its own; the container check is what can, because it
   denies the `cd` on the spot rather than deferring the question to whatever comes next. **An ancestor-only
   overlap (`cd M`, `cd ../../..`) is not this case** and stays allowed for the `cd` itself: it is far enough
   from the surface that a second, separate call starting there still has to name something concrete before
   this gate can act on it, which is exactly what `surfaceEntered` continues to cover *within* a single
   command — `cd "$main" && git clean -fdx` denies through `surfaceEntered` gating the second segment, not
   through the container check, because `M` itself is not inside any container.

   **The `namesSurface` text check restores parity with what every other segment already gets** — `cd` had
   its own path-resolution-based judgment instead, which trusts `resolveFrom` to correctly turn a word into
   an absolute path. `resolveFrom` reads ordinary Windows and POSIX absolute paths; it does not translate an
   MSYS/Git-Bash path (`/c/Users/…/wt/.tlc/harness`, which plain `resolve` turns into an unrelated path on
   whatever the current drive happens to be, not the `C:\Users\…` a real MSYS layer would produce) or a
   `\\?\`-prefixed extended-length one. Both resolve to a location that overlaps nothing this gate can see,
   while the segment's own text still spells out the real, relative structure underneath the mangling — the
   same gap `namesSurface` already exists to close for every non-`cd` verb.

   **The container itself is `machineHome()`'s parent only when `machineHome()` has the conventional
   `<container>/harness` shape** — `~/.tlc/harness`, where the parent `~/.tlc` is meaningfully "the
   container." `machineHome()` is `machineHome()` unconditionally otherwise (`machineContainerOf`,
   `conventionalNames`, both keyed off `projectStateDir`'s own layout, no literal): an operator's own
   `$TLC_HOME` (`TLC_HOME_FROM_ENV` unset or `"1"`, meaning it *was* chosen, not `tlc-exec`'s own fallback with
   `"0"`) can be anything — `~/tlc`, `D:/tlc` — and taking its parent as a container swept the operator's
   entire home directory, or entire drive, into a no-`cd` zone. `machineHome()` itself — the exact path the
   harness reads and writes — is the narrowest correct container when the shape does not match.

2. **A `cd`/`pushd` destination, or `-C`'s value, that overlaps a surface without landing in its container
   counts as an implicit reference** (`overlapsSurface`, `surfaceEntered`). For `-C`, to the rest of its own
   segment (through the ordinary word scan, unchanged). For `cd`/`pushd`, to every segment that follows within
   the same command (`checkPolicySurface` carries `surfaceEntered`, OR'd forward, never cleared) — this is
   what `git -C <main> clean -fdx`, `cd <main> && git reset --hard`, `cd .. && tar -xf x.tar` need: none of
   them name a path the gate can see on their own. **The root exclusion is per-surface, not global**:
   `resolved === root` only exempts the surface that root owns. A linked worktree's main checkout `M`
   contains the worktree `W`'s surface (`W` is nested inside `M`), so `cd M` / `-C M` is a reference to *`W`'s*
   surface even though `M` is exempt from its own. `cd <W's own root>` stays exempt, unchanged from upstream.
   **`-C` with an unresolved value** (`$X`, `$(...)`) makes the location unknown rather than absent — folded
   into the same `opaque` signal an unrecognized global option already produces, since `checkGitSegment` only
   ever runs once the segment already matters.

3. **`git merge` is a reader only in a narrow, explicit `--ff-only` form** (`isFastForwardOnlyMerge`). Every
   condition has to hold: flags drawn only from `{--ff-only, -q, --quiet}`, `--ff-only` present, exactly one
   ref operand that does not itself reference a surface, and **every candidate location the invocation might
   actually be running from — every tracked cwd, or every `-C`-resolved location when `-C` is given — is a
   tracked root or an ancestor of one**, checked with `every`, not `some`. A single root-reachable candidate
   used to be enough to vouch for the whole set, which is a side door: a `cd` to a genuinely unrelated
   directory joins the tracked candidates without objection (nothing about it overlaps anything), and a later
   `cd "$main"` would then make `some()` true even though the unrelated candidate itself has no tracked root
   under it at all. `every()` closes that without needing to know in advance which of several candidate cwds a
   real shell actually ended up in. **This is an explicit trade-off, argued once rather than re-litigated per
   case**: a fast-forward at a root updates the working tree with content already committed, reachable, in the
   object database — the same shape `git merge x`, run plainly anywhere in `W` that never cites the surface,
   is already allowed by this gate today. Whether that committed content *should* have reached this machine is
   the concern of the integrity baseline a commit lands through, not the floor.

4. **`cd`/`pushd` is opaque under any environment-assignment prefix, or an `env` wrapper carrying one**
   (`cdHasOpaquePrefix`). `CDPATH=`, `HOME=`, `OLDPWD=`, or any other `X=…` immediately ahead of the resolved
   `cd`/`pushd` — or `env` itself appearing anywhere before it — denies outright. `cd -` is opaque the same way
   once the segment names the surface some other way. A bare `cd`/`pushd` with no operand resolves to `$HOME`.

5. **The runtime surface check excludes `$HOME` itself, and anything above it, from its ancestor direction —
   the same exemption a project's own root already gets.** Restoring the ancestor direction (`cd ~/.tlc` is an
   ancestor of `~/.tlc/harness`, needed so that lands as a hit) also made `$HOME` itself count as an ancestor
   of the runtime state dir whenever the runtime home is conventionally nested under it — `find ~ -name x.log`
   and `cp notes.txt ~` denied on exactly that (common) machine shape. Only a path *strictly inside* home, and
   still an ancestor of (or equal to) the runtime state dir, counts. Item 1's container is derived from
   `machineHome()` for the same underlying reason this check already was: `tlc-exec` sets `$TLC_HOME` to the
   install path with `TLC_HOME_FROM_ENV=0` to say "not an operator's own choice," and using raw `$TLC_HOME`
   directly swept unrelated siblings of that install path into the container — item 1's own layout check is
   the further refinement that an *operator's* `$TLC_HOME` (`TLC_HOME_FROM_ENV="1"`) needs, which this
   ancestor-direction check does not, because it never takes a naive parent of anything in the first place.

6. **The config-equality check goes back through `isInside`, not `===`**, restoring the case-insensitive
   comparison Windows' own filesystem already has.

7. **`git`'s known global-option list grew three entries** (`--no-advice`, `--no-lazy-fetch`, `--list-cmds`,
   documented in `git help git`), so carrying one does not make an otherwise-clean read opaque.

8. **The tokenizer (`floor.tokenize.ts`) no longer treats a `&` glued to a `>`/`<` as the background-job
   separator.** `N>&M`/`>&M` (fd duplication, `2>&1`), `N<&M` and `&>file`/`&>>file` (bash's combined
   stdout+stderr redirect) all carry a `&` next to a redirect operator; splitting on it regardless turned
   `git log … dev 2>&1 | head -20` into a segment ending `2>` and a second, one-word segment `1` — which,
   under `surfaceEntered`, read as a non-reader verb and denied an everyday pipeline. The `&` is dropped
   (not kept) whenever it is glued to a `>`/`<`, collapsing every one of these forms to the plain `>`/`<`
   operator every rule in this file, including `redirectTargets`, already parses correctly — dropping rather
   than keeping is what keeps `>&file`'s real target intact rather than corrupted by a leading `&` glued onto
   it. A lone `&` (background) still separates.

   **The `&` is dropped only when the `>`/`<` it is glued to was itself appended bare — not quoted, not
   escaped** (`lastCharWasBareRedirect`, tracked directly rather than read back out of `current`'s trailing
   character). `current.endsWith(">")` cannot tell a genuine operator from a `>` that arrived inside quotes
   (`"a>"`) or behind a backslash (`\>`) — both leave the same trailing character in `current` either way.
   `echo "a>"& python3 -c "…"` swallowed the `&` on exactly that confusion, folding a real second command into
   an argument of `echo` and hiding it from every rule in this file, not only this one — confirmed against
   real bash (`echo "a>"& touch q1; wait` creates `q1`) before fixing. `lastCharWasBareRedirect` is set `true`
   only by the one branch that appends a bare, unquoted, unescaped `>`/`<`, and is cleared by every other
   branch that touches `current` — quoted content, an escaped character, `$(`/`${`-depth punctuation. `>`/`<`
   also joined `ESCAPABLE`, so `\>`/`\<` now consume as one literal character the way real bash treats them,
   rather than falling through as a backslash followed by a separate bare `>`/`<`.

   **`redirectTargets` (`floor.policy-surface.ts`) now reads every `>`/`>>` in a word, not only the first.**
   Once a dropped `&` folds into the word it touches, a word can carry more than one operator — `2>&1>surface`
   tokenizes to the single word `2>1>surface`, and reading only the first `>` reported `1>surface` as one
   opaque target, never reaching the real write target after the *second* `>` (confirmed against real bash:
   `echo x 2>&1>f; cat f` writes to `f`, the target of the last `>`). The same gap pre-dated this round for
   `>/dev/null>surface`, spelled with no `&` at all. Every fragment between one operator and the next, or
   after the last one, is now reported as its own target; a fragment that never turns out to be a real
   filename (the bystander `1` in `2>1>surface`) costs nothing to name, silently dropping one that is does.

## Why

**Three independent-Verifier probes, three different failure shapes, the same underlying cause running
deeper each time: an overlap was being asked a narrower question than the one that actually protects the
surface.** Probe one (25 regressions) found that bounding the ancestor match repaired the reads but reopened
writes aimed at a main checkout through the same ancestor path. Probe two (16 more) found that restoring the
match and gating *segments* through `surfaceEntered` still left `cd $main` alone, in one Bash call, unable to
stop `git clean -fdx` in a *second* call from reaching the same shell's now-relocated cwd — because
`surfaceEntered` is state carried inside one evaluation of one command string, and the floor is invoked once
per tool call with no memory of the last one's `cd`. Probe three's own `S5`–`S7`/`S25` rows are exactly this
gap: `cd .tlc/harness` alone, denied nothing, because nothing in *that command* proved unsafe once `cd` itself
went back to being judged as harmless. The fix is not a fourth layer of segment-tracking — no amount of
same-command bookkeeping closes a gap between two different commands — it is restoring a decision the first
two rounds had each, in turn, judged too broad: `cd`/`pushd` landing *inside* the surface's own container is
refused on the spot, not deferred to whatever the gate is trusted to catch next.

**Item 3's `every()` fix is what keeps `--ff-only`'s trade-off scoped to what it actually argues.** The
trade-off is about merging *at a root*. A tracked-cwd set that includes even one candidate with no root under
it at all is a set this gate cannot make that argument about, regardless of whether a *different* candidate
in the same set happens to be a root — `some()` let the argument through anyway, on the strength of a
candidate that was not necessarily where the invocation was actually running from.

**Item 5's `$HOME` exemption and item 1's `machineHome()`-based container are two symptoms of the same
category of bug**, both introduced by earlier rounds of this record: an ancestor-direction check, added to
close a real gap, swept in more than the gap that motivated it — first the runtime state dir's ancestors up
to and including `$HOME` (round 2), then, when the container concept came back, the raw `$TLC_HOME` value's
own ancestors up to system temp (round 3, caught before shipping this time, in `cost.ts` rather than by the
Verifier). Recorded here because the shape recurs: broadening a check to close a hole is also how a check
becomes broader than the hole.

## Trade-offs

**The container check and `surfaceEntered` overlap in what they catch, and that overlap is intentional.**
`cd "$main" && git clean -fdx` is caught by `surfaceEntered`, not the container check (`M` is not inside any
container); `cd .tlc/harness` alone is caught by the container check, because there is no later segment for
`surfaceEntered` to gate. Neither mechanism is redundant with the other — removing either reopens exactly the
gap the other does not cover.

**`isFastForwardOnlyMerge`'s location gate is stricter than "not inside a surface" — it requires a root or an
ancestor of one, specifically**, checked against every tracked candidate. A location that is an ancestor of a
*project* root but not itself tracked does not qualify either, because `isRootReachable` only asks about
tracked roots.

**`cd -`'s "cites the surface" check reads the segment's own text, not the accumulated chain** — `surfaceEntered`,
once set by an earlier `cd`, still gates everything after it regardless, so a `cd -` following an
overlap-setting `cd` denies through item 2, not through this narrower text check.

**`env`'s own grammar is not parsed** — its mere presence ahead of a `cd`/`pushd` is enough to deny, the same
posture taken for every other wrapper this gate does not specifically understand.

**`xxd`/`rg --pre` stay in `PROVEN_READERS` unchanged** — both can write through flags this gate does not
inspect (`xxd -r` reverses a hex dump back to a file; `rg --pre` runs an arbitrary preprocessor), a
pre-existing upstream gap this record does not fix. What item 1 closes is the combination: `cd .tlc/harness &&
xxd /x/in config.json` denies on the `cd` itself, before `xxd`'s own allowance would ever matter.

## Not decided here

- **`export CDPATH=…`/`export HOME=…` in an earlier segment, or inherited from the invoking shell's own
  environment.** The opaque-prefix check reads only an assignment word immediately ahead of `cd`/`pushd` in
  the *same* segment.
- **`.claude/settings.json` (project-relative) as a protected path (D5).** No floor rule guards it today.
  Reported, not fixed.
- **`--separate-git-dir` and git submodules.** `mainWorktreeOf` reads only the linked-worktree shape and
  correctly returns `null` for both rather than guessing, but no equivalent second-surface protection exists
  for either.
- **`mainWorktreeOf`'s cache holds `null` for the life of the process** — exact for a directory's worktree
  relationship at the moment it was first asked, not for the rest of the machine's uptime.
- **`xxd -r` / `rg --pre` as writers.** Named above as a real, pre-existing gap, out of this record's scope.
- **MSYS/Git-Bash path translation (`/c/...`), 8.3 short names (`TLC~1`), and junctions/symlinks are not
  resolved — only read as text.** `namesSurface` (item 1) catches the common case, where the segment's own
  text still names the surface even though `resolveFrom` cannot make sense of the path, but it is a text
  match, not a translation: a path built entirely at runtime (`$(...)`, already covered by the unresolved-word
  rule) or one that reaches the surface only through a junction or symlink `resolveFrom` never dereferences is
  outside what a lexical check — the same posture this whole file takes everywhere else — can see. Teaching
  `resolveFrom` any of these forms was judged out of scope: it is shared by every rule in this file, not only
  `cd`'s, and a wrong translation would be a correctness bug with a much wider blast radius than the case it
  would fix.
